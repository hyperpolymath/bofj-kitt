= Environments: what the kit provisions, and what each can reach

The proof toolchain manifest (`../proof-toolchain/toolchain.kyaml`) says
*which tools* the estate uses. This directory says *which environments*
those tools are projected onto, and records what each environment was
measured to reach. Design: `docs/proposals/environment-of-environments.adoc`.

[cols="1,3",options="header"]
|===
|File |What it is

|`environments.kyaml`
|One entry per environment class (workstation, agent session, CI runner,
devcontainer, Guix shell, sealed container, BoJ-registered view): how tools
get in, whether fetched binaries may run, which container runtime exists,
who reads its capability record, and a `measured` block.

|`probe-reachability.sh`
|Sends one HEAD request per URL in `hosts.txt` (or, with `--get`, one GET
for the first byte only, capped at 64 KiB when the server ignores the
range) and prints the HTTP status this environment saw, as text or as one
JSON object. Keeps no body, executes nothing. Its output is what goes
into one dated block in an entry's `measured` list: one block per
environment instance probed, never merged with another instance's.
`tests/probe_reachability_test.sh` checks it offline with stub `curl` and
`ldd` executables.

|`hosts.txt`
|The hosts the toolchain manifest's `method` column fetches from.

|`rendered/<class>/`
|Generated by `tools/proof-toolchain/provers.sh render` from the class's
`render` block in `environments.kyaml`: `setup.sh` (the setup script, at
most 100 lines of at most 200 bytes, every download pinned by SHA-256),
`allowed-hosts.txt` (the Limited-network allowlist: exact host names, at
most 20), `allowed-hosts-mcp.txt` (the MCP connector endpoints that plugin
connectors reach directly, kept apart from the toolchain hosts and their
cap; present when the class lists `mcp-connector-hosts`) and `env-vars.txt` (variable names only). Never hand-edited:
`provers.sh render --check`, run in CI by `tests/provers_test.sh`, fails
when a committed file differs from what the manifests render. Render also
refuses an allowed host that the class's latest `measured` block does not
show answering, unless the entry says why under `unmeasured`.
|===

== Reading a `measured` block

`reachable` means the request returned 2xx or 3xx (206 for a ranged GET).
`range-ignored` means a `--get` request was answered with the whole body,
so curl stopped at the 64 KiB cap: the host answered and ignored the
range. The probe does not inspect the body, so this does not show the
file is served (an error page over 64 KiB looks the same).
The probe asks only for the first byte, so it does not show whether the
host can resume a download. A host that answers some tries and resets
others is recorded under `intermittent` with the counts seen. `refused` is a 403
from the environment's proxy. `auth-required` is a 401: the host answered
and wants a token, which the probe does not supply. `tls-failed` means the
host's certificate is not in the environment's CA bundle. A container
registry's `/v2/` endpoint may answer `401` (wants a token) or `405`
(method not allowed for HEAD); both mean the registry answered, and
neither says whether an anonymous token flow would succeed. The manifest
records such hosts under `registry-answered` with the codes seen.

Proxies and hosts can answer HEAD and GET differently, as the registries
do. Confirm a HEAD `refused` with `--get` before recording it, and say in
the `measured` block which method produced each code.

`execute-downloaded` under `measured` takes one of three values:
`true` (a fetched binary was run), `false` (a fetched binary was present
and the environment refused to run it), or `denied-before-download` (the
attempt was stopped before any bytes moved, so running was never
observed). It is recorded only when an attempt was actually made.

A probe of a GitHub release *landing page* or of `api.github.com` says
nothing about release *assets*: the asset download path redirects to
`release-assets.githubusercontent.com`, which the probe follows
separately. Record the asset outcome, not the landing page's.
A successful HEAD, or a one-byte GET, does not establish that a full
download is permitted or that an executable ran. Record full downloads and
execution attempts separately as manual measurements; the probe does not
produce them.

A block is a fact about one environment instance on one date. It is never
copied from one environment class to another.

== Applying a rendered setup to an environment

This repository renders the files and never applies them. Changing the
cloud environment is the owner's step (or a session's environment-editing
tool, which puts an approval card in front of the owner). Nothing here may
change it on its own.

. Run `tools/proof-toolchain/provers.sh render --check`. It confirms the
  committed files match the manifests.
. Open the environment's settings: the cloud environment menu in the
  session title bar, then Edit.
. *Setup script:* paste the whole of `rendered/agent-session/setup.sh`.
. *Network access:* Limited, with package registries allowed. Add every
  host in `rendered/agent-session/allowed-hosts.txt` (the toolchain hosts,
  at most 20) and in `allowed-hosts-mcp.txt` (the MCP connector hosts, kept
  apart). The platform accepted 27 hosts on 2026-11-13.
. *Environment variables:* set the names in `env-vars.txt`, each marked
  `required` or `optional`. The file holds names only. Values live in the
  environment's settings and never in this repository.
. Start a new session. The setup script runs only when a container is
  built fresh, not when a session resumes.

The setup script is bash. The platform runs it as root while the container
is built, after the session's repositories are cloned and before Claude
starts. It is non-interactive, idempotent and at most 100 lines of at most
200 bytes, and it holds no secrets. Every download is pinned by SHA-256
and checked before it is unpacked; every apt package is pinned to a
version. It exits 0 even when an item fails, so a bad item never stops a
session from starting.

== The `!!!` lines and the setup report

Two places print `!!!` lines, both on purpose:

* *The setup script*, on stderr while the container is built:
  `!!! bofj-kitt setup: <id> <FAILED|UNAVAILABLE>: <detail>`. These appear
  in the environment's setup log, not in a session's chat. Every item, good
  or bad, is also a tab-separated line (`id`, status, detail) in
  `/var/lib/bofj-kitt/setup-report.tsv`, with status `PRESENT`,
  `INSTALLED`, `FAILED` or `UNAVAILABLE`. `doctor` reads that file.
* *The SessionStart hook* (`.claude/hooks/session-start.sh`), on stdout in
  every session: `!!! WARNING: ...` for a signing problem, for drift, and
  for the list of `UNAVAILABLE` ids. It also writes
  `.session/capability-record.json`, which is runtime output and is not
  tracked. The hook always exits 0 and never installs anything.

`UNAVAILABLE` does not mean the script broke. It means nothing installed
that tool, and the record says why. `kyq`, `deed` and `k9` are
`UNAVAILABLE` on purpose until a pinned release of each exists.

== Isabelle (measured 2026-11-14)

The setup pins `Isabelle2026_linux.tar.gz` by SHA-256 and unpacks it at
`$PREFIX/isabelle` (`tar.gz-tree`; the archive has one top directory).

* *URL.* `https://isabelle.in.tum.de/dist/...` answers 301 to
  `http://dists.isabelle.cit.tum.de/...?token=Isabelle` (plain http). The
  agent proxy cannot reach port 80 on that host and answers a bare 503, so
  a `curl -L` of the documented URL fails. The setup pins the https form on
  `dists.isabelle.cit.tum.de` directly; it needs `?token=Isabelle` (403
  without). That bypasses the site's redirect. Because the host may change
  how it serves this, a failure shows up as `FAILED download` in the report.
* *Integrity.* Isabelle publishes no checksum or signature (`.sha256`,
  `.asc`, `.sig`, `SHA256SUMS` all 404). The hash `858c995b...e48d` is from
  two identical full downloads on 2026-11-14, so it proves the bytes did not
  change since, not that they are the authors'. The SHA-256 pin is what
  protects the install.
* *Size and time.* 1,412,134,191 bytes; downloads took 77 s and 101 s;
  unpack 23 s; 2.7 GB on disk. The measured setup run added Isabelle to a
  container that already had the other items: 1 m 34 s in all. One
  download run in parallel with another was reset by the peer after 437 MB,
  so a slow or reset download is possible; the script's `--retry 3` and
  `--max-time 900` apply, and the transfer would need to stay above about
  1.6 MB/s to finish within 900 s (measured 14 to 18 MB/s).
* *Runs.* `isabelle version` printed `Isabelle2026` in 7.7 s on the first run
  (`execute-downloaded` true). Doctor reports `isabelle PRESENT`.
* *Allowlist.* `isabelle.in.tum.de` and `dists.isabelle.cit.tum.de` are
  both on the allowlist (19 hosts). The owner's Default environment is
  Unrestricted, so the allowlist matters only for a Limited fallback.

== Verified against real apt (2026-11-13)

`rendered/agent-session/setup.sh` from commit `6aebb6b` was run as root in
a disposable cloud session container, against the real apt archive and the
network that session had:

* *First run:* exit 0 in 1 m 42 s. `zstd`, `just`, `agda` 2.6.3, `coq`
  8.18.0, `elan`, `nickel` 1.18.0, `yq` v4.53.3, `lean` 4.13.0, `julia`
  1.13.3, `z3`, `cvc5`, `podman` 4.9.3 and `guix` 1.4.0 reported
  `INSTALLED`; `openssh-client` was already `PRESENT`; `kyq`, `deed` and
  `k9` were `UNAVAILABLE` as declared. Nothing reported `FAILED`.
* *Second run:* exit 0 in about 1 s, 14 `PRESENT` and 3 `UNAVAILABLE`.
* *Doctor afterwards:* 15 present, 0 drift, 36 unavailable. The 36 are
  tools the script does not install (why3, verus, Kani, Isabelle, hol4 and
  others).

Known gaps from that run:

* A bare `lean` outside a Lean project prints "no default toolchain
  configured". The script unpacks the 4.13.0 toolchain and elan lists it,
  but no elan default is set. Whether a project whose `lean-toolchain`
  names v4.13.0 resolves it was not tested.
* Isabelle was not installable on 2026-11-13: under Limited its host reset
  the TLS handshake on 6 of 6 tries. On 2026-11-14, under Unrestricted, it
  answered every try, and the setup now installs Isabelle2026 (see
  "Isabelle" below). Limited was not re-tested, so whether the reset
  returns under Limited is unmeasured.
* The network policy was not re-recorded for the run itself. The host
  probe taken earlier that day recorded Limited.
