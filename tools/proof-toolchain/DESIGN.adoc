= Proof toolchain: design
:toc:

One declared set of provers, solvers and translators, made available
wherever estate proofs run: the workstation, online agent sessions, CI
runners, and the echidna family's dispatchers. Which prover carries which
obligation is decided by `3-practice/PROOF-POLICY.adoc` in `standards`; this
kit decides how those tools get onto a machine and how a machine reports
which of them it has.

Status: design, not built. Nothing here installs anything yet; the build
steps are in <<plan>>.

See also `../environments/` and
`docs/proposals/environment-of-environments.adoc`: the environment classes
this toolchain is projected onto, with measured reachability. Those
measurements (2026-10-27) refine the assumptions below: the agent session
probed there *could* reach `opam.ocaml.org` and `alire.ada.dev`; it
*could* fetch a concrete GitHub release asset, as assumed; and it *could
not* reach release landing pages or `api.github.com`, so a `pin:
resolve` entry cannot be resolved from a session and `install` must read
the concrete asset URL from the lock. Reachability is measured per
environment and per path, not assumed per class.

== The problem it solves

The same tools are installed four different ways today, and each way fails
differently:

* *The workstation* (`~/developer/tools`, see `../workstation/`) installs
  through rustup, cargo, elan, pack, Alire and opam, with full network. It
  works, but nothing records which versions it holds.
* *Online agent sessions* (Claude Code cloud sessions, claude.ai skills)
  cannot reach `opam.ocaml.org`, `alire.ada.dev`, or GitHub source
  archives. They can reach GitHub *release assets*. So Creusot's Why3 back
  ends, Lambdapi, Dedukti, agda2dedukti and Idris2 cannot be built there at
  all, and every session that needs them fails or reports a leg it never ran.
* *CI runners* have the network but not the time: a cold opam build of
  Creusot's back ends or of agda2dedukti costs tens of minutes per job.
* *Dispatchers* (echidna, echidnabot, proof-burrower) need binaries at known
  paths and a way to tell which provers a host really has.

== The design in one line

Build once where the network is open, ship one relocatable-by-prefix bundle
as a release asset and a container image, and let every target unpack the
same bytes and report what it holds in one machine-readable form.

== Parts

[cols="1,3",options="header"]
|===
|Part |What it is

|`toolchain.kyaml`
|The manifest, and the only hand-edited file. One entry per tool: its id,
its role under PROOF-POLICY, how it is built, its pin, and the command that
proves it runs. Roles are listed below.

|`toolchain.lock.json`
|Tool-owned lock, written only by the bundle build (I-JSON, JCS). Records the
resolved version, the source URL and the SHA-256 of every input, and the
SHA-256 of the produced bundle and image digest. Never hand-edited.

|Bundle build (CI)
|A workflow on a full-network runner builds every tool into the fixed prefix
`/opt/hyperpolymath/provers`, then publishes
`provers-<date>-x86_64-linux.tar.zst` as a GitHub release asset of this repo
and an OCI image (Wolfi base) containing the same tree, both pinned in the
lock.

|`provers.sh install`
|Fetches the bundle named in the lock, checks its SHA-256, and unpacks it at
the prefix. The same command serves the workstation, a session's setup
script, and a CI job. A release asset is reachable from all three.

|`provers.sh doctor`
|Reports each manifest entry as `PRESENT <version>`, `DRIFT <have> != <lock>`,
or `UNAVAILABLE <reason>`, as text and as one JCS object. It never reports a
tool it could not run as present (PROOF-POLICY §6).

|`provers.sh render`
|Regenerates `../workstation/PROVERS-SOLVERS.adoc` from the manifest, so the
human index cannot drift from the declared set. What a given machine has
installed is `doctor`'s job, not `render`'s.

|Guix manifest
|The tools that Guix packages are also projected into a Guix manifest for
Guix-primary hosts. The bundle is the sealed escape hatch for the tail Guix
does not carry (estate ruling 2026-05-18).
|===

=== Why a fixed prefix

opam switches, elan toolchains and Alire builds embed absolute paths, so a
bundle built at one path does not run at another. Every target therefore
unpacks at `/opt/hyperpolymath/provers`. The install step of <<plan>> also
adds `/opt/hyperpolymath/provers/bin` to the workstation's `env.sh` `PATH`
beside its existing homes (it is not there yet); the
tools it already builds natively stay where they are until the bundle covers
them.

=== Which systems the bundle runs on

Copying native binaries to the same path does not make them run on a host
with an older C library or missing shared libraries. The bundle is therefore
built inside a pinned builder image whose glibc is the declared minimum, with
every shared library that is not part of that baseline copied under
`lib/` and found through the binaries' run path. Before a bundle is
released, `provers.sh doctor` must pass on each supported target: the CI
runner image, the agent-session image and the workstation's distribution.
The lock records the builder image digest and the glibc minimum.

=== Why a release asset first, image second

Agent sessions can download a release asset but usually cannot run a
container engine. CI and the dispatchers can run containers. So the tarball
is the primary artefact and the image wraps the same tree, rather than the
other way round.

== The closure rule

The bundle is complete only if nothing a tool needs at run time comes from
the host or the network. Three rules keep it so:

. *Everything a tool loads is an entry.* Runtimes (Rust toolchains, a Java
  runtime), libraries (the Agda standard libraries, Agda2Dedukti's theories,
  Aeneas's Lean backend) and every Lean toolchain a consumer pins are
  manifest entries, fetched and hashed like the tools themselves.
. *Coupled versions derive from the tool that drives them.* Why3 and why3find
  come from Creusot's `creusot-deps.opam`, Charon from Aeneas's `charon-pin`,
  Dedukti and Lambdapi from Agda2Dedukti's tested revisions. Nothing coupled
  is resolved on its own.
. *A producer is checked end to end.* Where a tool's output is consumed by
  another (a translator feeding a checker), its `verify` runs the pair on a
  bundled smoke input instead of a help probe.

rustup and elan are configured never to install a toolchain on demand, so a
toolchain missing from the bundle fails loudly instead of being fetched behind
the lock's back. An entry that locks several toolchains is verified once per
toolchain, so `doctor` cannot pass on whichever one happens to be the default.

== Roles

Each manifest entry carries one role. The roles are PROOF-POLICY's mapping,
plus the supporting tools the mapped provers need.

[cols="1,3",options="header"]
|===
|Role |Tools

|`policy:rust` |Creusot (with Why3 and Why3find)
|`policy:ada` |gnatprove (SPARK)
|`policy:engineering` |Idris2 (with pack)
|`policy:theory-source` |Agda with its standard library. The standard libraries are their own entries, so the bundle fetches, pins and hashes them like any other input. Two versions side by side, 2.6.3 and 2.6.4.3, because the theory repos pin both; a repo selects its own.
|`policy:recheck` |Rocq (`coqc`), Lean (elan with pinned toolchains; no Mathlib)
|`transport` |agda2dedukti, Dedukti (`dkcheck`), Lambdapi. agda2dedukti tracks particular Agda versions; the manifest records which Agda it accepts.
|`exception:rust` |Kani; Aeneas with Charon (PROOF-POLICY §4.1)
|`exception:recorded` |TLA+ (`tlc`); Isabelle, HOL Light, HOL4, ACL2 and Mizar (supplementary only). The last four were added 2026-10-27 so a kit-provisioned environment can serve every backend in echidna's default core set; PVS, the remaining core backend, is a licensed binary and belongs to the sealed-container tail, not the bundle.
|`runtime` |Rust toolchains (rustup, the toolchains Creusot and Kani pin), a Java runtime for the `tlc` launcher, Poly/ML for HOL4 and SBCL for ACL2, bundled rather than taken from the host
|`backend` |Z3, CVC5, Yices, Alt-Ergo, E prover, Vampire
|===

The estate's own `echidna` (the prover dispatcher) is a *consumer* of this
toolchain, not part of it. Trail of Bits' Echidna (a Solidity fuzzer), which
`../workstation/PROVERS-SOLVERS.adoc` currently lists, is a different tool
that shares the name; the manifest names it `echidna-solidity` if it stays.

== How the estate uses it

* *echidna and echidnabot* read `provers.sh doctor --json` to decide which
  `ProverKind` backends a host can actually serve, instead of probing
  binaries one by one.
* *The BoJ server* receives the same JSON when the kit registers an
  environment (README, "register"), so a remote caller can see which
  provers an environment offers before dispatching to it.
* *The proof-craft skill* stops carrying its own installer:
  `install-toolchains.sh` becomes `provers.sh install` plus `doctor`, and the
  skill's canonical copy lives in this kit.
* *Recheck records* (the echidna hand-off of 2026-10-26) can cite the lock's
  translator and prover versions by hash, which answers "which agda2dedukti,
  which Agda" for every transported leg.

== Build plan (stacked PRs)

. This design and the manifest. `provers.sh render` regenerates the
  workstation index from it.
. `provers.sh doctor`, text and JSON. Useful at once on the workstation,
  before any bundle exists.
. The bundle build workflow and `provers.sh install`. It produces the first
  release asset and image and writes the lock.
. Consumers: the session setup-script snippet, the CI usage pattern, the
  echidna capability read, and proof-craft's switch to `provers.sh`.

This is the kit's first concrete capability (roadmap M2–M4). It needs no
choice of implementation language: the scripts are POSIX shell over `yq`
(Go) and `jq`.
