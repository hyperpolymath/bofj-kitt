Status: proposal, 2026-10-27. The roster below was read from echidna's
`crates/echidna-core/src/prover_kind.rs` (141 variants), its
`docs/PROVER_COUNT.adoc` (12 core, 105 implementation files, 46
type-discipline variants with no binary) and `src/rust/provers/` (the binary
each backend spawns). The existing lists were read from the `stuff-of-awe`
organisation on the same date.

Format note: echidna's prover registry is cited as `provers.a2ml`
because that is the file today. A2ML is retired in favour of the deed
format (standards `1-formats/deed/spec/abnf/deed.abnf`); the `binary`,
`family` and `owner` fields proposed below target echidna's deed once
the `.a2ml` to `.deed` conversion (ruling D313) lands there.

This proposal lives in bofj-kitt because the kit is where the estate decides
which provers an environment carries; the lists are the human index of the
same roster. Nothing here creates a repository; see <<decisions>>.

== The rule for cutting lists

One list per *family of reasoning tool*, not per tool and not per echidna
tier. echidna's tiers are CI cadence (every PR, nightly, smoke), which is
no help to a reader. Families are what a reader searches for: "an SMT
solver", "a model checker", "a logical framework". The exceptions are the
anchor systems of echidna's core, where a per-system list is what the
upstream community expects and where the estate already has three (Coq,
Agda, Idris2).

Where a maintained upstream list exists, fork it, as the estate did for
`awesome-zig` and `awesome-gleam`, and specialise. Where none exists,
create. Each new repository takes the shape `awesome-nickel` has (README,
EXPLAINME, governance, the estate CI set, the Idris2 link-validation tests).

== The formal route

The lists are data about tools, and the one property worth stating
formally is *coverage*. Each tool has one *owning* list, the entry that
carries its description; any other list may mention it as a
cross-reference (Z3 in `awesome-constraint-solving` for its optimiser,
Sledgehammer in `awesome-atp`, TPTP in `awesome-logical-frameworks`). The
property is then: every variant of `ProverKind` has exactly one owning
entry across the priority-1 and priority-2 lists, cross-references are
unlimited but must point at the owner, and every tool the kit manifest
names has an owner. With the registry of option D (an `owner` field per
tool) that is a finite relation and the check is a test (`TESTED`), the
same kind of check `awesome-nickel` already runs in Idris2 over its links.
It is not worth a theorem; it is worth a gate.

== Aspects

Maintenance:: Twenty-one repositories is the real cost. The estate CI set
(governance, link check, Idris2 validation tests) is what keeps a list from
becoming a 2018 snapshot like `awesome-provable`. Do not create a list
without it.
Licensing:: Lists are CC0 (as `awesome-idris2`) so they can be forked and
merged upstream freely; `awesome-coq` carries coq-community content under
its upstream licence and must keep saying so.
Attribution:: Forked lists keep upstream history and the original
maintainers in `MAINTAINERS`.
Accessibility:: Each list is one AsciiDoc file with a table of contents;
no images carry information.
Template fit:: The standards spec-templates put `awesome-idris2` and
`awesome-nickel` on the `cli-tool` archetype with ABI-1..5 proofs. A list
has no ABI. The template needs a `list` or `docs` archetype before
twenty-one more lists inherit the wrong obligations.
